How the Integration Airlock actually decides

A walkthrough of the multi-runtime reference implementation — what each mechanism proves, how the six-gate pipeline evaluates a single request, and how a decision becomes durable evidence. Every diagram below maps directly onto a scenario you can run yourself in the live demo.

01 · Architecture

Three independent trust domains, one airlock

Nothing crosses the integration boundary merely because software requests it. The airlock sits between requesting assets and three runtimes — each one a separate trust domain bound to its own policy, not a shared destination with three names.

Figure 1 — One airlock, three independently policy-bound trust domains. Asset identity and authority are evaluated fresh at whichever runtime is the actual target.

This matters because the alternative — one global policy applied everywhere — can't tell the difference between a request bound for a low-stakes operational system and one bound for physical infrastructure. Binding each runtime to its own profile is what makes a genuinely different answer at RT-INFRA possible, not just a relabeled copy of the answer at RT-OPS.

02 · Evaluation

Every request walks the same six gates

Regardless of which runtime is the target, every single request is evaluated through the same ordered sequence. A failure at any gate halts the pipeline immediately — nothing downstream of a failed gate ever runs.

Figure 2 — The six-gate pipeline. The position of a failure is itself diagnostic information, not just a yes/no outcome.
Commit-before-execute. Gate 6 writes the audit record before the crossing is allowed to proceed — not after. A request that would PERMIT but fails to commit to the ledger is treated as a LOCKOUT, not a silent PERMIT with a missing record.
03 · Mechanism 1

Same asset, same request, two different answers

A demo that lets one runtime stand in for all three would be illustration, not proof. The actual test: hold the requesting asset completely fixed — same registration, same authority level, same kind of request — and change only the target runtime. If the decision changes too, each runtime is genuinely evaluating independently rather than relabeling a shared answer.

Figure 3 — The only variable that changed is the target runtime. That alone is enough to flip the outcome.

Run S14 and S15 back to back in the demo and the evidence exports for each will show the same asset_id and the same authority_level, differing only in target_runtime_id and the resulting decision. That pairing is the actual proof — not a description of the architecture, but two real, reproducible evaluations that disagree for a documented reason.

04 · Mechanism 2

Permission at one hop grants nothing at the next

A request can cross more than one runtime in sequence — RT-OPS, then RT-CMD, then RT-INFRA. Each hop in that chain is a real, independent evaluation of the same six gates, not a single check whose result is carried forward. Clearing hop one says nothing about hop two.

Figure 4 — A chain is only as trustworthy as its weakest hop. CH2 proves the chain stops the instant that hop fails, rather than completing on the strength of the hops before it.

Each hop in a chained crossing is given its own event ID, so a chain can't accidentally trip the replay-lockout gate against itself as it moves hop to hop. The thing being tested is whether authority genuinely re-qualifies at every boundary — and CH2 is the asset that proves it does, by failing exactly where it should.

05 · Mechanism 3

Two ways a group can look individually clean

Every member of a coordinated request can pass its own gates one-by-one and the group can still be the problem. There are two distinct ways that happens, and the airlock checks for both independently — neither check substitutes for the other.

Figure 5 — Three individually-permitted members exceed the same-runtime threshold as a group. No single gate caught this; only the group-level check does.

This is the easier of the two violations to picture: too many requests hitting the same destination at once, regardless of how clean each one is on its own. The harder case is the opposite shape — never enough at any single destination to trip that check, but spread suspiciously wide.

Figure 6 — Each runtime is fine on its own; the violation only exists at the level of how many distinct runtimes one group is touching at once.
Two checks, not one. Same-runtime concurrency asks "how many requests hit this one destination." Cross-runtime fan-out asks "how many distinct destinations does this one group touch." C2 is constructed so the first check finds nothing — proving the second check is doing real, independent work, not just restating the first.
06 · Evidence

A LOCKOUT can be overridden — never erased

A coordinated LOCKOUT caused by the group-level checks above isn't necessarily the end of the story — a human reviewer may have legitimate reason to approve it. What matters is how that approval gets recorded.

Figure 7 — Append-only by construction. Approving an escalation adds a record; it does not touch the one that came before it.

This is the same discipline that governs the audit ledger itself at gate 6 — a decision, once committed, is a historical fact rather than a draft. An override that quietly rewrote the original LOCKOUT would itself be exactly the kind of unsupervised action the airlock exists to prevent. The override button only ever appears for genuine group-level LOCKOUTs, never for a request that failed an individual gate — approving an escalation can't and shouldn't fix a ghost asset or a missing registration.

07 · Conclusion

The airlock proves what it refuses, not just what it allows

Every diagram in this guide describes the same underlying claim from a different angle: permission is never inherited, never assumed, and never durable beyond the single request it was granted for. A clean individual gate result says nothing about a group's concurrency, a chain's next hop, or a runtime's own floor — each of those is re-evaluated independently, every time, with no shortcut earned by having passed before. That is the entire point of the Integration Boundary Invariant: not that the airlock blocks bad requests, which any gate can do, but that it cannot be talked into treating a new boundary crossing as already-decided. The scenarios in the live demo exist to make that claim falsifiable rather than rhetorical — S14/S15, CH1/CH2, and C1/C2 are not illustrations of the architecture, they are the architecture failing exactly where it should and passing exactly where it should, on demand, every time it is run.
